## 一、设计哲学与三大红线

### 1.1 核心公式

> **单条回复质量 ≈ 话题新鲜度 × 人称一致性 × 输出整洁度（乘法关系，任一趋零整体趋零）**
>
> 状态体系（14 维情绪、双层记忆、好感度）只影响"语气"——是加分项；
> 上面三个乘数项全是**上下文工程与输出卫生**——是及格线。

业界对标结论（恋语 / N.E.K.O / Soul / SillyTavern / astrbot 生态的调研结论，
详见 `AI陪伴对话效果优化技术调研.md`）：**把及格线交给确定性代码，把加分项交给模型**。
这就是"不同质量的模型都能输出相似体验"的全部秘密——四层防御：

| 层级 | 机制 | 本项目落点 |
|---|---|---|
| L1 预防 | 严格 prompt 模板 + one-shot 示例 + 视角契约 | `chat.rs::build_cognitive_prompt` |
| L2 容错 | 解析失败不崩：XML→JSON→逐步提取→降级 | `chat.rs::parse_cognitive_response` |
| L3 清洗 | 确定性后处理：标点归一化、去冗余、剥离署名 | `post_process.rs` |
| L4 兜底 | 本地分段算法、复读拦截、PASS 沉默 | `post_process.rs::split_segments`、`topicLedger.ts` |

### 1.2 三大红线（违反即回退）

1. **禁止在 LLM 已生成的自然文本上做字符级"拟人手术"**。
   历史教训：`inject_imperfections`（句首插"那个……"、句中插"对了，"、句号替换省略号）与
   `emotion_consistency` 后缀注入，是用户感知"莫名其妙的感觉""多一个。/、"的直接来源，
   已于 2026-08 全部拆除。拟人化的犹豫/走神由 prompt 层约束 #9 让模型**在生成时自然写出**
   （`chat.rs` 重要约束第 9 条）。后处理只允许做**确定性、幂等、语义无关**的修正
   （标点归一化、去重复标点、剥署名）。

2. **所有后台 LLM 调用必须有显式开关，且默认关闭**。
   历史教训：`autoAnalysisEnabled` 默认 `true` 且每 2 轮触发思考/分析/总结三次后台调用，
   用户"压根没开启"却在烧 API。规则：任何新增的生成式调用点，必须接入设置页开关 +
   `debugLog` 记录，默认值必须是"用户显式开启后才跑"。

3. **主动消息必须允许"沉默"**。
   每条主动路径的 prompt 必须提供 PASS 选项（`<pass/>`），前端检测到 PASS 静默放弃、
   不计配额。主动消息永远不能是"必须生成一条内容"的强制任务。

## 二、系统架构总览

```
┌─────────────────────────── 前端 (React + Zustand) ───────────────────────────┐
│  chatStore            正常聊天编排：上下文组装 → 调 Rust → 渲染分段 → 记账     │
│  proactiveReplyStore  主动消息编排：3 条路径 → 闸门 → 调 Rust → PASS 检测      │
│  topicLedger          话题账本：recordTopic / buildTopicLedgerPrompt（防重复） │
│  characterMindStore   12/14 维情绪、好感度、记忆的落库                          │
│  memoryAnalysisStore  后台记忆任务配置（自动分析/定时分析，默认全关）            │
│  intentGate(services) 统一主动闸门：睡眠/预算/被无视退避                        │
│  debugLogStore        分类日志（pipeline/proactive/memory/system/learning）     │
└──────────────────────────────────┬───────────────────────────────────────────┘
                                   │ invoke('process_message') / ('process_post_pipeline')
┌──────────────────────────────────▼───────────────────────────────────────────┐
│                          Rust 后端 (Tauri, src-tauri/src)                     │
│  chat.rs        process_message：prompt 组装 → LLM → 认知链解析 → 情绪/好感度  │
│  ai.rs          多 Provider 的 LLM 调用（模型角色路由：认知/后台等）             │
│  post_process.rs run_post_pipeline：清洗→拦截→分段→卫生 12 步                  │
│  anti_cliche.rs  回复风格随机化（seed 与 prompt 同源）+ 反 AI 腔温度            │
│  ai_tasks.rs    后台任务：generate_thinking / generate_analysis /             │
│                 generate_conversation_summary / generate_reflection           │
└───────────────────────────────────────────────────────────────────────────────┘
```

**职责划分原则**：
- 前端负责**编排与状态**（何时调、调谁、把什么上下文给后端、结果怎么落库渲染）；
- Rust 负责**生成与卫生**（prompt 组装、认知链、后处理、拦截）；
- 两端通过 `ProcessMessageRequest / ProcessMessageResponse`（`chat.rs:19` / `chat.rs:122`）契约通信；
  前端类型定义见 `src/lib/tauriBridge.ts`。

## 三、Rust 主管线 `process_message` 详解

入口：`src-tauri/src/chat.rs:418 pub async fn process_message(req, app)`。
阶段事件通过 `emit_stage`（chat.rs:187）推给前端 `PipelineDebugPanel` 实时展示。

### 3.1 请求关键字段（`ProcessMessageRequest`，chat.rs:19）

| 字段组 | 字段 | 说明 |
|---|---|---|
| 角色 | `character_name / personality / background / style / catchphrases` | 人格来源；`custom_personality` 可前端热覆盖（V3） |
| 状态 | `emotion_values_json`（12 维 JSON）、`affinity_level / affinity_stage` | 由 `characterMindStore` 读取 |
| 对话 | `messages_json`（完整历史，含 role/content）、`user_message` | 历史无名字标注，人称锚定靠视角契约 |
| 记忆 | `memories_json`（相关性检索结果）、`conversation_summary` | `build_memory_summary` 转 prompt |
| 环境 | `current_time / timezone`（时区感知）、`time_gap_hint`（跨时距提醒）、`user_profile` | |
| 热更新 | `custom_system_prompt / custom_personality / custom_care_guidance / custom_environment_awareness` | 前端 `promptConfigStore` 面板即时覆盖，无需重启 |
| 主动 | `proactive_suffix` | 主动消息专属任务块（见第六节） |
| 拦截 | `forbidden_text`（违规词）、`recent_replies`（最近 AI 回复） | Rust 端复读/违规拦截的数据源 |
| 后处理 | `segment_config`（enabled/threshold/maxSegments/mode/minSegmentLength/protectPairedSymbols）、`reply_delay_ms(+random)` | |
| 生成 | `temperature / max_tokens`（前端自适应计算）、`use_full_cognitive`、`model_role`、流式开关 | `compute_max_tokens`（chat.rs:342）对推理模型加 reasoning buffer |

### 3.2 Prompt 组装顺序（`build_cognitive_prompt`，chat.rs:1480）

**这是全项目最重要的 300 行**，顺序即优先级（越靠后离生成越近、权重越高）：

1. `你是「{name}」` + 当前时间（**时区感知**：按角色时区偏移换算本地时间，chat.rs:1491）
2. **【视角契约 / POV Contract】**（chat.rs:1685）——人称锚定，解决"上班辛苦了"主客体翻转：
   - "我"= 角色自己，"你"= 用户；
   - 用户说的事是**用户的**事，回应时用"你"指代他；只有自己的事才用"我"；
   - **永远不替用户说话/下结论他的感受**；不确定主客体先在心里判定再动笔。
3. 【环境意识】虚拟陪伴场景声明（可被 `custom_environment_awareness` 覆盖）
4. 【你的人格】性格/背景/说话风格（可被 `custom_personality` 覆盖）+ 口头禅提示（"只是风格参考，不是固定台词"）+ 用户画像
5. 【当前状态】好感度（数值+阶段）、12 维情绪摘要、时距提示（"距离上次对话约 N 小时"或"一直保持联系"）、混合情绪 top-3 提示（`build_emotion_mix_hint`）、关系阶段策略（`build_relationship_stage_hint`）
6. 【潜台词感知】字面 vs 深层需求
7. **【易错对照 / Common Mistakes】**（🆕 P2-3 few-shot 反混淆库）：✗/✓ 三组对照——主客体
   （"上班好辛苦"必须用"你"回应）、话题防重复（刚聊完不再问）、作文式回复 vs 口语+空行分段
8. 【重要约束】9 条，其中：
   - #6 聊天不是写信：禁止落款署名（署名只属于日记/留言）；
   - #7 禁止"嗯的、的呢？"式冗余"的"病句；
   - **#8 聊天式输出契约 + 分段契约**：一次回复 1~2 句（最多 3 句），禁止编号列表；内容多时**用单独空行分隔多条消息**——"空行是消息边界，系统会按条拆分发送，这是你唯一的分段方式"；
   - #9 语气词/犹豫在生成时自然写出（红线 1 的 prompt 侧落点）。
9. 【反配合机制】约每 8-12 轮 1 次温和分歧；用户情绪崩溃时绝不反驳
10. 【脆弱性展示】约每 6-10 轮 1 次轻微示弱
11. 【关怀方式】负面情绪承接策略（可被 `custom_care_guidance` 覆盖）
12. 【对话摘要】跨模型快速回忆（前端 `chatContextBuilder.buildConversationSummary` 从 summary 记忆拼接）
13. 【相关记忆】`build_memory_summary`（chat.rs:1793）
14. `custom_system_prompt` 追加（最后生效）
15. `proactive_suffix` → 包装为【本次任务：主动发起对话】块（chat.rs:1784）

**约束 #8 的分段契约**已附具体示例（🆕 P1-1）：「今天去了新开的甜品店！」与「蛋糕超好吃，下次带你去。」
之间空一行 = 两条独立消息——配合 `split_segments` 的空行优先消费（5.2）构成生成端↔消费端闭环。

### 3.3 生成与解析

- 生成：`ai.rs` 按模型角色路由 Provider；推理模型走原生推理区（`build_parse_source` 会把推理内容并入解析源，chat.rs:992）。
- 解析：`parse_cognitive_response`（chat.rs:2121）三级降级：
  1. `parse_xml_cognitive`（chat.rs:2137）——`<thought>/<reply>/<update>` 标签；
  2. `parse_json_cognitive`（chat.rs:2283）——弱模型输出 JSON 时兜底；
  3. `extract_step`（chat.rs:2481）——按「中文标签 / 英文标签:」逐行提取（`感知/Perceive`、`话题/Topic` 等）。
- 回复提取：`extract_reply_from_cognitive_chain`（chat.rs:2002）+ `strip_all_xml_tags`。
- 情绪更新：`parse_emotion_deltas` → `merge_deltas_same_dim` → `apply_emotion_update`（chat.rs:2721），
  变化量钳制 ±5/情绪、好感度 ±3（认知链 prompt 中已写死，解析层再兜底）。
- OOC 检测：`detect_ooc`（chat.rs:2785）。

### 3.4 响应关键字段（`ProcessMessageResponse`，chat.rs:122）

`reply / segments / segment_delays / emotion_update / affinity_delta / topic / consult_raw / report_raw / thought_steps / parse_warnings / ooc_detected / stage events`

**`topic`（chat.rs:147）**：本轮话题（2-6 字），从认知链「话题 / Topic:」步提取（chat.rs:2214）。
前端收到后调用 `recordTopic(character.id, result.topic)` 记入话题账本（chatStore.ts:1309）——
这是主动消息防重复的时间函数数据源。**删除此链路会让主动回复退回"复读机"状态，禁止移除。**

## 四、认知链（思维链）格式与解析

认知与回复**同帧单次调用**完成（省 token、保证"想的"与"说的"一致）。当前为 8 个步骤槽位
（历史文档称"7 步"，实际含话题与用户情绪共 8 行输出要求）：

```
感知 / Perceive:（先判定主客体：用户说的是谁的事——用户自己的/第三方的/我的？再判断情绪状态）
评估 / Evaluate:（我该怎么做？考虑到双方关系）
代谢 / Metabolize:（我自己的情绪需要调整吗？只写定性判断，严禁数值）
决策 / Decide:（语气、长度、重点）
更新 / Update:（最终增量：sadness +2, joy -1, 好感度+1；情绪 ±5 内、好感度 -3~+3）
学习利用 / Learn:（用户喜欢的说话风格）
话题 / Topic:（**必填** 2-6 字，程序识别用）
用户情绪 / UserEmotion:（**必填** {"emotion":"love","intensity":80}，14 维之一）
```

- **感知步的第一句必须是主客体判定**——这是视角契约的认知链落点（解决"我说上班辛苦了她却说她辛苦了"）。
- one-shot 示例刻意选**主客体易混场景**（"今天加班到十点"→ AI 感知"用户自己加班"→ 回复主语用"你"）：
  few-shot 教一次比规则写十次有效。
- 机器消费字段（`UserEmotion`、`Update`、`topic`）key 全部 ASCII（N.E.K.O 同款踩坑：中文 key 在多语种模型下解析脆弱）。
- reasoning / 非 reasoning 两套指令模板（chat.rs:1543 / 1578），约束均为"<reply> 正文优先"。

**修改认知链格式的注意事项**：
1. 每改一处格式，必须同步 `parse_xml_cognitive` / `parse_json_cognitive` / `extract_step` 三条解析路径；
2. `ParsedCognitive` 结构体新增字段时，5 处构造点都要补齐（见 chat.rs:2374-2457 一带的默认构造）；
3. one-shot 示例必须与格式严格一致——模型对示例的服从性远高于对规则的服从性。

## 五、输出后处理管线 `run_post_pipeline` 详解

入口：`src-tauri/src/post_process.rs:1256`。输入 `PostPipelineRequest`（含各步骤开关），输出
`PostPipelineResponse { text, segments, segment_delays, aborted, abort_reason, logs, step_results }`。

### 5.1 十二步顺序（顺序即契约，不可随意调换）

| # | 步骤 | 函数 | 说明 |
|---|---|---|---|
| 1 | 清洗标记 | `clean_markers` | 剥 `<thought>/<reply>` 等标签、动作描写（`remove_action_descriptions`） |
| 2 | 拦截 | `is_duplicate`(LCS, 阈值默认 0.92) + `block_cliche`(违规词) | 命中即 `aborted`，前端丢弃本次回复 |
| 3 | 错字模拟 | `typo_sim` | 概率钳 ≤0.1 |
| 4 | 长度随机化 | `length_randomize` | 风格 seed 与 prompt 提示同源（`anti_cliche::select_reply_style_seeded`） |
| 5 | 分段（第一遍） | `split_segments` | 见 5.2 |
| 6 | 语气微调 | `tone_polish` | 受 `InjectionBudget` 约束 |
| 7 | 口语化 | `colloquialism` | 受 `InjectionBudget` 约束 |
| 8 | 智能标点 | `smart_punctuation` | |
| 9 | 说话节奏 | `speaking_rhythm` | |
| 10 | 最终净化 | `final_sanitize` | 顺序：`fix_redundant_de` → `normalize_punctuation` → `collapse_repeated_punct` → 空白归一 |
| 10.5 | 剥署名 | `strip_signature` | "——爱你的XX"式落款硬剥离（Bug1） |
| V8 | 分段重算 | `split_segments` | **始终按最终文本重算**（步骤 6-9 可能改文本；修复了"关闭分段时 segments 过期"的 P1-5 bug） |
| V7 | 段间延迟 | `compute_segment_delays` | 段长 × 情绪强度动态计算，随响应返回 |

**已被拆除的步骤**（勿以任何形式复活，见红线 1）：
旧 2.5 `emotion_consistency` 后缀注入、旧 2.7 `inject_imperfections`
（改口/省略号替换/走神插话/多余碎碎念）。代码中的重构注释见 post_process.rs:1318。

### 5.2 四维断句引擎（`split_segments`，post_process.rs:658）

分层降级设计，**优先消费模型按约束 #8 输出的空行边界**，无空行时才用本地算法：

1. **空行优先**：`\n\n` 分出的段直接作为消息（生成端契约的消费端）；
2. **四维断句**（无空行时的降级，对标 astrbot 四维引擎）：
   - 区间探测：`[min_segment_length, golden_max]` 黄金区间内找断点；
   - 优先级锚定：换行 > 句号 > 逗号（`split_into_sentences` / `find_natural_cut`）；
   - 弹性延伸：区间内无标点则延伸到下一个标点（`assemble_golden_range`），硬极限仍无则物理截断（`fallback_split`）；
   - 短尾合并：尾巴过短时撤回最后一刀（`merge_tiny_segments`）；
3. **成对符号保护**：`protect_paired_symbols`——引号/括号/书名号内不切；
4. **maxSegments 超限**：超出部分与最后一段直接相连（各句自带句末标点）。
   ⚠ 历史 bug：曾用 `join("，")` 硬拼完整句，产出"……了。，……吗？"怪标点——已修复，**不要再改回任何带标点的 join**。

### 5.3 标点归一化（`normalize_punctuation`，post_process.rs:1112）

解决"多一个 ."""的来源——模型中英文标点混用：
- 中文语境（标点**紧邻 CJK 字符**）下的 `.` `?` `!` `,` `;` `:` `~` → 全角 `。？！，；：～`；
- 保护：英文句子（前后无 CJK 不转）、小数（3.5）、千分位、URL、省略号序列（`...` 中的点不转）；
- 配套 `collapse_repeated_punct` 收敛连续重复标点。

**新增标点规则的验收标准**：`cargo test`（post_process tests 覆盖 clean/segment/normalize 场景）+
手工验证 "I'm fine. 哈哈" / "3.5" / "哈哈..." / "好的!哈哈" 四类样本。

## 六、主动消息体系

### 6.1 三条路径与统一闸门

| 路径 | 入口 | 来源标记 | 说明 |
|---|---|---|---|
| 回复后主动 | `proactiveReplyStore.triggerProactiveAfterReply` | `callback`(P2) | 正常回复后按概率+冷却触发 |
| 定时主动 | `proactiveReplyStore.sendScheduledReply` | `scheduled`(P1) | 用户配置的定时点触发 |
| 链式主动关心 | `chainProactiveStore` | `chain`(P2) | 受每日预算约束（默认 8 条/天） |

所有路径出站前必须过 `intentGate`（`src/services/proactive/intentGate.ts`）：
1. **睡眠拦截**（AI-Life 判定睡觉时静默）；
2. **安静时段**（🆕 P2-4）：23:00–07:30 本地时间一律静默（`task` 来源除外），`isQuietHours()`；
3. **用户活跃跳过**（🆕 P2-4）：用户最近 5 分钟内发过消息时，自发类主动（定时/链式/AI-Life）暂不打扰
   （`callback` 回复后主动是对话自然延续，不受此限）；活跃时间戳由 `notifyUserMessage` 记录；
4. **每日预算**：chain 受预算（`chainDailyBudget`，被无视退避：连续 2 次减半、3 次当日静默）；
   定时主动另有 `scheduledMaxPerDay`（默认 5/天，proactiveReplyStore 内计数）；
5. **被无视退避**：主动消息 2 小时未回应记一次无视；用户任意消息 → `notifyUserMessage` 解除；
6. `checkGate` 无副作用；**`recordSent` 仅在实际发送成功后调用**（PASS/拦截不计配额）。

### 6.2 话题账本（`src/services/topicLedger.ts`）——防重复的时间函数

**问题的根源**（2026-08-29 前的历史设计）：回复后主动的 prompt 里有"接续锚点"——
"你上一条回复是「…」。你的新消息**必须直接接着这段话往下说**……这是唯一的续写起点"。
用户说吃饭 → AI 回吃饭 → 回复后主动被强制接着说吃饭 → 下一轮锚点又是吃饭……**话题永远无法逃逸**。

**现行设计**：
- **记账**：每轮 Rust 回复的 `result.topic` → `recordTopic(characterId, topic)`（chatStore.ts:1309）；
  localStorage 持久化（key `topicLedger:v1`），按角色隔离，环形 30 条，同话题合并计数。
- **新鲜度判定**：`classifyTopicAge` —— `fresh`(<1h) / `cooldown`(1~24h) / `stale`(>24h)。
- **prompt 注入**：`buildTopicLedgerPrompt(characterId)` 生成最近 8 条话题清单（含"几分钟前/几小时前/天前"
  人性化时间 + 聊过次数）+ 规则文本（1 小时内严禁再提；当天不主动再问；隔天最多"上次你说的…"重温一次）。
- **消费方**：`triggerProactiveAfterReply` 与 `sendScheduledReply` 的 suffix 末尾注入
  （proactiveReplyStore.ts 中搜索 `buildTopicLedgerPrompt`）。

### 6.3 PASS 机制（主动消息的可选沉默）

- prompt 指令：切入点菜单第 5 项——"都没有合适的 → 只输出 `<pass/>`，保持沉默"；
- 前端检测：`sendProactiveMessage` 中 `/^\s*(<\s*pass\s*\/?\s*>|\[pass\]|pass\s*\/?)\s*$/i` 命中 →
  debugLog 记录 PASS → `return null`（不发送、不 `recordSent`、不更新 `lastProactiveTime`）；
- Rust 回复为空时的放弃日志会注明"模型可能选择沉默或被 Rust 拦截"。

### 6.4 主动消息 prompt 设计模板（现行，勿回退）

两处 suffix（proactiveReplyStore.ts）共用同一骨架——**切入点优先级菜单**（对标 N.E.K.O 两阶段决策：
Phase 1 规则层管"要不要开口"= 闸门+账本；Phase 2 LLM 管"说什么"= 菜单）：

```
回复后主动：
1.【收尾】上一轮挂着没说完的事 → 补一句或确认
2.【此刻生活】正在做的事/刚注意到的小事 → 随口分享
3.【时间氛围】饭点/深夜/下班/天气 → 应景的话
4.【旧话题】隔了一天以上、真有新内容 → "上次你说的…"（最多一次）
5. 都没有 → <pass/>
硬性禁止：账本里"几分钟前/几小时前"刚聊过的话题一个字都不要再提（尤其反复问吃饭/睡觉/累不累）
格式：只说一件事，15~40 字，像随手发的微信

定时主动：
1.【没下文的事】对方之前提到要做的事/答应的事/挂着的问题 → 问结果
2.【此刻生活】今天遇到的小事 → 分享
3.【时间氛围】早晨问昨晚/午饭问吃什么/深夜劝休息
4.【旧话题】隔天以上有新由头 → 带出
5. 都没有 → <pass/>
硬性禁止：账本里当天聊过的禁止再提；同一话题无论隔多久最多主动提起一次
```

两处 suffix 均注入 `buildTopicLedgerPrompt(characterId)` 与 `buildLifeNowHint(characterId)`：
- **话题账本**（P0-1）：最近话题清单 + 时间函数规则，防重复追问；
- **此刻生活提示**（🆕 P2-1）：该角色开启 AI-Life 生活引擎时，把 `currentActivity`
  （活动名/地点/心情/刚发生的事）作为切入点2【此刻生活】的真实素材——
  主动消息的内容来自"生活"而非上一条聊天记录（Soul DailyAgent 思路的轻量落地）。

**核心原则**：主动消息的话题来源必须与"上一条聊天记录"解耦（生活/没下文的事/时间氛围/隔天旧事），
节流靠闸门，防重复靠账本，沉默是合法输出。

## 七、后台任务与 API 调用闸门矩阵

**2026-08-29 修复的 bug**：`autoAnalysisEnabled` 默认 `true` + 每 2 轮触发 → 用户"压根没开启"
却每 2 轮跑 3 次后台 LLM 调用（思考/分析/总结）。已改为**默认全关**，并把 localStorage key
升为 `memory-analysis-config:v2`（旧 key 下持久化的配置携带旧默认值 `true`，会覆盖新默认，
故强制重置；用户需在设置页重新开启）。

| 后台任务 | 函数/命令 | 闸门（全部满足才跑） | 间隔 |
|---|---|---|---|
| 记忆提取 | `extractMemories`（前端） | `memoryTasksAllowed` && 距上次 >5min | 5 min |
| 状态反思 | `generateReflection`（前端） | `memoryTasksAllowed` && `reflectionEnabled` && 负面情绪或强度≥70 && >30min | 30 min |
| 思考记忆 | Rust `generate_thinking` | `shouldRunAutoAnalysis`（= memoryTasksAllowed && `autoAnalysisEnabled` && N%触发轮==0） | 每 N 轮 |
| 用户分析 | Rust `generate_analysis` | 同上 | 同上 |
| 对话总结 | Rust `generate_conversation_summary` | 同上 | 同上 |
| 定时分析 | 同上 trio | `scheduledAnalysisEnabled` && 距上次 ≥ 设定分钟 | 定时 |

其中 `memoryTasksAllowed = (v2Config.dualLayerMemory !== false) && (autoAnalysisEnabled || scheduledAnalysisEnabled)`
（chatStore.ts:1968-1975）——**分析开关全关时提取/反思一并停止**（这是有意的耦合，
注释见 chatStore.ts:1970，避免"关闭了还在跑"的日志困扰）。

主动回复路径（proactiveReplyStore）内的提取/反思走同一套开关与间隔
（`v2Settings.dualLayerMemory !== false` + 时间间隔），与主聊天同源。

**给后续开发者的提醒**：新增任何后台生成式调用，照此矩阵加开关 + 间隔 + debugLog，
且默认值必须为关。检查清单见第九节。

### 第九批（NapCat 连接看门狗：双向检测 + 自动恢复，2026-08-30）

新增 `src/services/botWatchdog.ts`——解决"断连期间生成的回复被直接丢弃、且无任何恢复手段"：

**双向检测**：
- 下行：监听 Rust `bot-status` 事件（`connected`/`disconnected`/`stopped`/`error`，反向 WS 与正向客户端两模式的事件 Rust 侧已齐备）；任意外部消息到达（`notifyInbound`）同样证明下行存活；
- 上行：外发成功/失败计数（`markOutboundOk`/`markOutboundFail`），连续 2 次失败告警"NapCat 可能已断开"（只告警一次直到恢复）。

**自动恢复（任意一端发送消息即触发补发）**：NapCat 重连（connected 事件）、收到外部新消息、应用侧任一次外发成功——三者任一发生都立即补发待发队列；另有 60 秒周期扫描兜底。

**待发队列**（localStorage `botOutbox:v1`，刷新不丢）：外发失败自动入队，单条 10 分钟 TTL、最多补发 3 次、队列上限 20 条——宁可少发也不迟到轰炸。断连/重连/补发全程写 `bot` 类调试日志。

接线点：`useBotMessageHandler` 启动看门狗（App 挂载）；`flushPendingBotMessages` 入站通知；两条外发函数成败挂钩。

**回归**：`tsc` ✅、`vitest` ✅、`build` ✅。

**验收行为（手工测试清单）**：

## 九、开发规范（新增功能必读）

1. **新增 LLM 调用点**：必须有设置页开关（默认关）+ debugLog 记录 + 走 `memoryTasksAllowed` 式闸门矩阵。参考第七节。
2. **禁止机械注入**：不得在生成后的文本上插入与语义无关的词句/标点（红线 1）。拟人化表达一律走 prompt 层（认知链约束 #9）。
3. **机器字段 ASCII 化**：供程序解析的输出字段（情绪/更新/话题/决策）key 用英文；展示性内容用中文。
4. **新主动路径**：必须 (a) 过 `checkGate`；(b) 成功发送后 `recordSent`；(c) prompt 提供切入点菜单 + PASS；(d) 注入 `buildTopicLedgerPrompt`；(e) 硬性禁止清单引用账本时间函数。
5. **认知链改动**：同步三条解析路径 + `ParsedCognitive` 全部构造点 + one-shot 示例（第四节）。
6. **后处理改动**：保持每一步确定性、幂等；新增步骤跑 `cargo test`；分段相关改动注意 V8 重算语义（5.1）。
7. **prompt 改动**：`build_cognitive_prompt` 的块顺序即优先级，不要重排；约束条目追加放末尾，不要插队。
8. **提交前**：`cargo check`（src-tauri）+ `npx tsc --noEmit` + `cargo test` 三绿。
9. **日志纪律**：用户可感知的 debugLog 是排查"莫名其妙行为"的唯一线索——放弃/拦截/降级路径必须留日志（沿用 A6.6 原则）。
